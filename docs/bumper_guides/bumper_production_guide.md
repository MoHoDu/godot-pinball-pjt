## 0. 먼저 읽을 것 — 기획서와 코드가 어긋나 있다

작업 전에 이 절을 반드시 확인한다. **가이드 v0.2의 범퍼 목록과 현재 코드의 범퍼 목록이 다르다.**

### 0-1. 가이드 7종 중 실제 작업 대상은 6종

가이드 5-5절에 **`장난감 기차는 개발 취소됨, 구현하지 말것`** 이 명시돼 있다.
그런데 같은 절에 형태·색상·선화·연출·SFX 규격이 그대로 남아 있어 오해하기 쉽다.
**기차는 만들지 않는다.** 이 가이드의 STEP1 마스터에도 포함하지 않았다.

### 0-2. 구슬 미끄럼틀은 코드에 아트 슬롯이 없다

### 텍스처 규격

| 항목 | 값 | 근거 |
|---|---|---|
| 마스터 해상도 | **1024×1024 RGBA** | 최대 표시 지름 128px 의 8배 |
| 배경 | 완전 투명 | |
| **알파 bbox** | **== 캔버스 (여백 0)** | ★ 아래 |
| 글로우·충격파 | 텍스처에 굽지 않는다 | VFX 레이어가 별도 처리 |

#### ★ 알파 bbox == 캔버스 규칙

공 리소스에서 두 번 밟은 지뢰다(→ `docs/ai_memory/project_ball_texture_fixed.md`).
표시 크기 계산이 **텍스처의 긴 변**으로 나누기 때문에 **캔버스 여백 = 표시 크기 손실**이 된다.
구본 `ball.png` 는 1104px 캔버스에 공이 84%만 차서 실제 53px 로 그려졌고,
충돌은 57.6~64px 이라 최대 11px 어긋났다 → 검수 즉시 FAIL.

`bumper_master.py` 의 `finalize()` 가 알파 bbox 로 크롭 → 정사각 패딩 → 1024 리사이즈로 이 규칙을 강제한다.
생성 시 채움률을 표준출력에 찍으니 **가로·세로 모두 100%에 가까운지 확인**한다.

#### ★ 구슬 미끄럼틀은 다른 범퍼 크기로는 성립하지 않는다

공 지름이 **64px** 다(`pinball.gd` `DEFAULT_BALL_DIAMETER`).
미끄럼틀은 공을 **통로에 담아** 옮기는 장치라, 통로 바닥 폭이 공 지름보다 넓어야 한다.

STEP1 마스터의 통로 바닥 폭은 표시 지름의 **0.30 배**다. 즉

- 표시 지름 112px(다른 범퍼 수준) → 통로 바닥 **33px** → 64px 공이 안 들어간다
- 표시 지름 **240px** → 통로 바닥 **72px** → 공이 담긴다

`.tres` 가 없어 확정 지름이 없으므로 검수 시트는 **240px 가정값**을 쓴다.
실제 값은 개발에서 정해야 하고, **다른 범퍼와 같은 100px 대로 잡으면 안 된다.**

#### 충돌 원과 외곽선의 관계

가이드 2절·9절이 **"충돌 판정 범위와 보이는 외곽을 최대한 일치시킨다"** 고 못 박는다.
표시 지름이 충돌 지름보다 4~8px 크다. 이 차이는 **외곽 잉크선 두께**로 소비한다.

- 잉크선 바깥 경계 = 표시 지름
- 잉크선 안쪽 경계 ≒ 충돌 지름

STEP1 마스터의 외곽선 두께는 캔버스 기준 약 5.2%(1024에서 약 27px)로,
128px 표시 시 약 3.3px, 92px 표시 시 약 2.4px 다. 위 관계를 만족한다.

### ★ STEP1 마스터를 그대로 믿지 말 것

STEP1 은 **코드로 그린 배치 도면이지 완성 아트가 아니다.** 단추처럼 단순한 것은 쓸 만하지만
북의 목마, 솜 내부는 조악하다. 그래서 STEP2 에서 **형태판을 HIGH 가 아니라 MID 로 넣는다.**
HIGH 는 픽셀을 베끼고 MID 는 배치를 따르되 다시 그린다.

범퍼에 따라 형태판을 아예 빼고 텍스트만으로 뽑는 편이 낫다. 갈래는 `leonardo_prompts.md` 0절.

### 손그림 선 처리

가이드 2-2절이 요구하는 **"완전한 벡터 선이 아니라 약간 흔들리는 손그림 선"** 을
`wobble_circle()` / `wobble_path()` 의 저주파 노이즈로 구현했다.

- 외곽선: 끊기지 않고 실루엣을 확실히 잡는 굵은 선
- 내부선: 외곽선보다 얇고 불규칙, 좌우 완벽 대칭 금지
- 원은 전부 약간 찌그러뜨렸다 — "접시 동심원도 완전 정원 금지" 규칙

### 범퍼별 형태 결정 근거 (가이드 "범퍼별 보드 내 시점 및 탑뷰 표현 기준")

**단추** — 위에서 수직으로 본 원형 단면. 구멍 4개를 탑뷰에서 명확히 구분.
바깥 테두리와 안쪽 면의 명도 차이로 두께 표현. 목재 결은 윗면 안쪽에만.
옆면 노출·원근 표현 없음.

**솜** — 위에서 본 비대칭 구름형. 겹친 덩어리 7개의 합집합으로 실루엣을 만들고
내부 덩어리 경계선은 남기지 않았다(하나의 연속된 외곽선). 내부는 큰 곡선 위주.
천 조각과 봉제선은 외곽 일부에만. 중심 타격 위치는 비워 뒀다.

**용수철 인형** — 기본 상태는 둥근 얼굴이 범퍼 대부분을 차지하고 용수철은 가장자리 일부만.
타격 상태에서 얼굴이 위로 눌리며 압축된 용수철이 드러난다.
**두 상태의 형태 차이가 Bounce 기능을 전달하는 핵심**이라 프레임을 2장으로 나눴다.

**장난감 북** — 넓은 원형 북막이 주요 면적, 바깥에 두꺼운 북틀 링.
깊이는 링 안쪽 그림자와 테두리 두께로만 암시. 북채·손잡이 없음.
북막 안 회전목마 말은 잔선 없이 큰 색면 실루엣으로만 넣었다(PDF 레퍼런스 지시).

**구슬 미끄럼틀** — 지지대·높은 측면 생략. 공이 지나는 통로 단면만.
진입부(좌상) → 접시 → 출구(우하)가 한눈에 연결된다.
출구 방향은 마지막 곡선 실루엣으로만 읽게 했다 — **화살표 장식 금지** 규칙.
아래쪽 얇은 그림자로 보드에서 떠 있는 높이만 암시.

**태엽 장난감 대포** — 원형 회전 받침대가 충돌 실루엣. 중심에 공 포획 위치.
포신은 중심에서 바깥으로 짧고 굵게, 포구 내부는 어둡게 처리해 앞뒤 구분.
바퀴는 이동 기능이 아니라 정체성 전달용 외곽 장식. 태엽은 포신 후방에 노출.
**받침대 동심원과 방향축을 회전 중심에 일치**시켰다 — 런타임 회전 시 어긋나지 않는다.

## 5. Godot 연결 — 아직 슬롯이 없다

**현재 범퍼 비주얼은 전부 프로시저럴이다.** `scripts/bumper-system/bumper_visual.gd` 의
`_draw()` 가 `BumperPresentationSettings.visual_style` 열거값에 따라 도형을 직접 그린다.
**텍스처를 받을 경로가 없다.**

즉 STEP1/STEP2 PNG 를 만들어도 **그대로는 게임에 안 붙는다.** 코드 변경이 선행돼야 한다.

### 제안 — 최소 변경 · 하위 호환

이 가이드에서는 **코드를 수정하지 않았다.** 범퍼 시스템은 `dev/bumper_reapair` 에서
수리 부품 작업이 진행 중이라 충돌 위험이 있고, 프로젝트 규칙상 승인이 필요하다.
승인 시 아래 형태를 권장한다.

1. `bumper_presentation_settings.gd` 에 텍스처 슬롯 추가

   ```gdscript
   @export var texture: Texture2D:
       set(value):
           texture = value
           emit_changed()
   ```

2. `bumper_visual.gd` `_draw()` 진입부에서 분기

   ```gdscript
   if presentation.texture != null:
       var diameter := bumper.settings.visual_diameter
       var size := presentation.texture.get_size()
       var scale_factor := diameter / maxf(size.x, size.y)   # ← 긴 변 기준
       var draw_size := size * scale_factor
       draw_texture_rect(
           presentation.texture,
           Rect2(-draw_size * 0.5, draw_size),
           false,
           Color(Color.WHITE, alpha)
       )
       _draw_durability(bumper, diameter * 0.5, curse)
       return
   # 텍스처가 없으면 기존 프로시저럴 경로를 그대로 탄다
   ```

3. 대포는 포신 회전이 필요하다. `_draw_cannon()` 이 이미
   `get_selected_launch_direction()` 을 읽고 있으므로,
   텍스처 경로에서도 `draw_set_transform(Vector2.ZERO, direction.angle(), Vector2.ONE)` 로
   같은 값을 쓴다. **마스터가 +X 기준으로 그려져 있어 각도 보정이 필요 없다.**

4. 용수철 인형은 상태별 텍스처 2장이 필요하다. 슬롯 하나로는 부족하므로
   `texture_hit` 을 추가하거나 `AnimatedSprite2D` 로 전환한다. — **별도 설계 필요**

### 주의 — 상태 표현이 프로시저럴에 묶여 있다

`_draw()` 는 텍스처만 그리는 게 아니라 상태도 표현한다. 텍스처로 갈아탈 때 같이 옮겨야 한다.

| 상태 | 현재 처리 | 텍스처 전환 시 |
|---|---|---|
| 비활성 | `alpha = 0.28` | `modulate` 로 유지 가능 |
| 복구 예고 | `0.55 + sin(t) * 0.25` 점멸 | 유지 가능. 단 가이드는 "아주 약한 떨림"을 요구 |
| 내구도 | `_draw_durability()` 가 실밥 스티치를 그림 | **텍스처와 별개로 남겨야 한다.** 위 제안 코드에서 유지 |

## 6. 검수 체크리스트

가이드 7절·9절 + 프로젝트 리소스 통과 기준(→ `docs/ai_memory/reference_art_pipeline.md`)을 합쳤다.

### 즉시 FAIL

- 역할·상태를 바로 알아볼 수 없다
- 실제 게임 크기(92~128px)에서 형태가 뭉개진다
- 범퍼가 공·선택된 플리퍼보다 눈에 띈다
- 장식과 실제 충돌 범위가 크게 다르다
- 기능색이 규칙과 반대로 쓰였다 (빨강을 범퍼 주색으로)

### 비주얼

- [ ] 보드(`#2E3A47` 짙은 남청색 목재) 위에서 종류가 명확히 읽히는가
- [ ] 공보다 먼저 눈에 들어오지 않는가
- [ ] 선택된 플리퍼보다 강하게 점멸하지 않는가
- [ ] 모든 범퍼가 청록/아이보리 위주로 획일화되지 않았는가
- [ ] 외곽선은 명확하고 내부선은 수작업 느낌인가
- [ ] 굶지마풍 선맛은 있으나 직접 복제처럼 보이지 않는가

### 탑뷰

- [ ] 정지 화면에서 실루엣만으로 종류를 구분할 수 있는가
- [ ] 범퍼 중심과 실제 충돌 판정 위치가 일치하는가
- [ ] 높은 옆면이나 장식이 공을 가리지 않는가
- [ ] 용수철 인형은 타격 전후 구조 차이가 명확한가
- [ ] 장난감 북은 북막이 주요 충돌면으로 읽히는가
- [ ] 구슬 미끄럼틀은 진입점에서 출구까지 경로가 한눈에 읽히는가
- [ ] 대포는 포신 방향과 공 포획 중심이 즉시 구분되는가

### 기술

- [ ] 알파 bbox == 캔버스 (채움률 가로·세로 100%)
- [ ] 배경 완전 투명
- [ ] 글로우·충격파가 텍스처에 구워지지 않았는가
- [ ] 대포 마스터가 +X 기준인가
